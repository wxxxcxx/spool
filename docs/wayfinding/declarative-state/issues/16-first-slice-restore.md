# 首切片是否自动恢复跨进程窗口绑定

## Question

当前window ID/PID/bundle/title及运行期CFHash incarnation未建立跨daemon身份连续性保证。首个后台列宽切片应仅实现原始意图保存、候选读取和可测试导入入口，默认不自动重绑定；还是必须同时解决跨daemon自动恢复？候选结构是保存范围描述，不代表创建旧分组或执行移窗。

## Context

完整跨重启恢复已暂缓；用户不要求旧兼容。需明确首切片可验收边界，不能宣称“有条件恢复”实际上具备未证明的平台能力。

## Answer

三方一致，按用户授权接受：首切片只实现新格式原始布局意图持久化、隔离候选读取和可测试的纯导入接口，不提供实际跨daemon自动重绑定或自动布局恢复。

- 保存结构是候选描述，不等于识别旧窗口、创建旧分组或对应当前Space。不得把数值ID、PID、标题或运行期CFHash当跨进程身份保证。
- 重启正常按本次原生观察和当前规则初始化；已存列宽不会自动应用。首切片也不承诺用户可操作的手动恢复命令。
- 纯导入接口接收调用者显式提供的可信当前映射，验证领域合法性和版本门禁，不自行猜身份、不直接调用平台。mock测试映射不证明真实跨进程匹配。
- 首片没有可信自动绑定提供者，不提供一个可开启却缺少保障的恢复开关。旧格式忽略不迁移，旧恢复路径不能与新意图writer并存。
- 对外区分accepted、saved、candidate-read、imported与native-applied；只读取到候选不能报告后两项成功。
- 跨daemon身份研究、实际自动匹配与停机冲突处理是后续恢复地图范围，不是本轮未清理的fog。
